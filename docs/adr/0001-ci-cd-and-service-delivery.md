# ADR 0001: CI/CD 与服务交付边界

- 状态：接受
- 日期：2026-08-22

## 背景

仓库包含 Spring Boot 后端、React Admin 和 Flutter Android App，目前没有线上 CI。
后端已有 Dockerfile、Flyway 迁移和 Docker Compose 运维方式，Admin 通过静态文件部署，
App 通过仓库内脚本生成 APK 或 AAB。

后端当前是模块化单体。现有架构约定要求在独立扩缩容、发布节奏、故障隔离或团队所有权
出现明确压力后再评估微服务，不能只因为未来可能拆分就提前增加网络和数据一致性成本。

## 决策

1. 使用 GitHub Actions 执行 PR、`main` 和 SemVer 标签流水线。
2. PR 与 `main` 必须分别验证后端单测、MySQL/Valkey 集成测试、Admin 冻结锁文件构建、
   Flutter 分析与测试，并对后端容器执行真实启动探测。
3. `vMAJOR.MINOR.PATCH` 注解标签触发发布。发布工作流重新执行同一组质量门禁，再构建
   GHCR 后端镜像、Admin 静态包和按开关启用的签名 AAB。
4. 后端部署只使用 GHCR 返回的镜像 digest，不使用 `latest` 等可变标签。构建记录包含源码
   SHA、镜像 digest 和 GitHub provenance attestation。
5. 生产部署归属 GitHub `production` environment，必须配置审批、固定 SSH host key、远端
   路径和凭据。`BACKEND_AUTO_DEPLOY` 未启用时，标签只发布制品，不连接生产主机。
6. 远端激活前创建 MySQL 备份并记录旧容器和镜像。数据库迁移不兼容时默认采用前向修复；
   只有明确声明迁移兼容时，才允许自动回滚到旧镜像。
7. 镜像构建封装为可复用工作流。未来出现真实微服务时，每个服务提供自己的构建上下文、
   Dockerfile、镜像名、健康检查和数据兼容说明，再复用该工作流。

## 未采用的方案

- 现在拆分微服务：缺少独立扩缩容和发布节奏证据，会增加跨服务授权、事务和运维成本。
- `main` 提交后直接部署生产：跳过 SemVer、人工审批和迁移兼容判断，回滚边界不清楚。
- 部署可变镜像标签：无法证明测试、签名和生产激活使用的是同一制品。
- 在发布机重新构建：会使验证过的源码与最终运行镜像失去一一对应关系。

## 结果

当前单体可以按一个服务交付，但流水线不把“一个仓库”等同于“永远只有一个镜像”。
增加微服务时不需要复制发布安全规则，只需增加新的服务调用方和对应部署适配器。
