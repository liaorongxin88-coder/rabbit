# NFC 碰一下选择：交互设计

- 状态：方案设计中，待业务确认
- 核对日期：2026-09-02
- 适用范围：Flutter App（Admin 不涉及）
- 前置阅读：[交互验收规范](../../project/interaction-acceptance-spec.md)、`app/.rule`

Admin 明确不做 NFC。`admin/DESIGN.md` 的 Non-goals 里写着
PC 工作台不出现 NFC 标签写入与解析、蓝牙、摄像头、MQTT 或硬件触发控件，
本文所有交互只发生在 App。

## 1. 七条性质在本专题的落法

`docs/project/interaction-acceptance-spec.md` 规定新交互必须证明七条性质。
逐条对照如下，其中第 6 条现在做不到，是本次要补的。

| 性质 | 在碰一下选择里的含义 | 现状 |
| --- | --- | --- |
| 1 失败看得见 | 提示渲染在按钮下方，随表单滚动，不用 SnackBar | `move.dart` 已经这样做 |
| 2 失败不毁输入 | 贴错标签只更新提示，不关闭表单、不清空已填字段 | 已满足，采集是表单上的附加动作 |
| 3 重复提交只生效一次 | 多选场景连贴同一张标签不重复加入；提交带 `requestId` | 需在多选态显式去重 |
| 4 批量前后都要交代 | 多选贴完说清加入几只、跳过哪只、为什么 | 当前只说「有 N 只可选，请在列表中选择」 |
| 5 边界拦住且说得清 | 拒绝时说出笼位标识和拒绝原因，不只说「不可选」 | 已满足 |
| 6 断网有活路 | 见 §3.2，当前断网即死路 | **不满足** |
| 7 窄屏大字号不塌 | 360×800、200% 字号下按钮与提示不溢出 | 需在提取构件时一并覆盖 |

## 2. 现有两份实现

碰一下选择今天有两份实现，各自缺对方有的东西。

| | `move.dart` 内联块（187 到 265 行） | `NfcRabbitPickerButton`（`event.dart` 1460 到 1482 行） |
| --- | --- | --- |
| 选什么 | 兔笼 | 笼内的兔只 |
| 是否可复用 | 否，写死在换笼弹窗的 State 里 | 是，已是独立 widget |
| 硬件可用性预检 | 有 | 无 |
| 候选歧义处理 | 不涉及 | 有，多只时让用户回列表选 |
| 文案 | 「该标签属于其它兔舍，未选中」 | 「该标签属于其他兔舍，未选择兔只」 |

`move.dart` 里那句预检的注释写得很清楚：写标签路径一直有这个检查，读取路径漏了。
`NfcRabbitPickerButton` 就是漏的那一个，用户在没有 NFC 的机器上点「碰一下」，
会对着一个永远不会响的提示干等。

两份文案连「其它」和「其他」都不一致。这不是洁癖问题：现场反馈问题时说的是提示原文，
两种写法会让人以为是两个功能。

## 3. 共享构件

### 3.1 两个选择器

按选中对象的类型分成两个 widget，都放 `lib/src/ui/core/widgets/`，
因为它们已经有两个以上真实调用方且契约稳定，符合 `app/.rule` 的提取门槛。

```text
NfcCagePicker    选中一个兔笼        参数：候选笼、可接收判定、已选回调
NfcRabbitPicker  选中笼内的兔只      参数：候选兔、是否允许多选、已选回调
```

`NfcRabbitPicker` 直接沿用现有 `NfcRabbitPickerButton` 的参数形状
（`houseId`、`candidates`、`idleLabel`、`waitingLabel`、`onSelected`、`enabled`、`allowMultiple`），
它已经过真机验收，不重新设计。搬家时补上硬件预检，并统一文案。

`NfcCagePicker` 从 `move.dart` 抽出来，把「可接收判定」从内部的 `_acceptsTarget`
改成外部传入的回调，因为四个入口对「什么笼算合法目标」的规则各不相同。

### 3.2 断网时仍能选中

这是本次交互上最实质的改动。

标签载荷本身就带着笼位标识：`NfcPayloadTarget.parse` 解出 `houseId` 和 `cageId`，
不需要任何网络请求。但现在两个选择器解析完还是要调 `POST /api/nfc/cages/resolve`，
断网时落进 catch，提示「读取标签失败，请重试」，重试多少次都一样。

改法是分两段：

1. 先用载荷里的 `cageId` 在**已经加载到本地的候选列表**里找。找到就直接选中，
   提示后面缀一句说明这次没有联网核验。
2. 联网可用时仍然调 `resolve`，用服务端返回的绑定视图覆盖本地结果。

这样做要交代清楚代价：载荷带 HMAC 签名，但密钥在服务端，客户端验不了。
跳过 `resolve` 等于接受一张未经核验的标签预选了某个笼位。
风险是有界的：预选结果用户看得见，而提交时服务端仍然完整校验签名与业务规则，
伪造标签最多让用户多点一次取消，不会写坏数据。

候选列表之外的笼位仍然拒绝，提示「未在当前兔舍找到该笼位」，与联网时一致。

## 4. 四个入口的具体交互

四个入口的宿主界面都已经存在，改动是在既有选择控件旁边加一个碰一下入口，
不新建页面。原有的选择方式一律保留，NFC 是并行的第三条路，不是替代。

### 4.1 商品兔转后备兔留种选兔笼（recvtK5FSRTAyo）

宿主：`lib/src/ui/rabbits/sheets/replacement.dart`，当前是 `RadioListTile` 列表（145 到 159 行）。

在列表上方加 `NfcCagePicker`。碰中的笼位直接选中对应的 radio 并滚动到可见位置，
不是只高亮。合法目标限定为后备兔笼或空笼，其余当场拒绝并说明：
「3-2-1 是商品兔笼，不能作为后备兔笼」。

### 4.2 场内生产入笼选断奶记录（recvtK8yseN9jM）

宿主：`lib/src/ui/rabbits/sheets/entry.dart` 的 `_CreateRabbitSheet`（1006 行起）。

这一条比其余三条多一跳。用户碰的是母兔所在的笼，要落到的是「这只母兔的哪一条待分笼记录」：

```text
碰标签 -> 笼位 -> 笼内种母兔 -> 该母兔的待分笼记录
```

四处可能断，每一种都要说清楚是哪一种：

| 笼里的情况 | 文案 |
| --- | --- |
| 没有种母兔 | `C-01 没有种母兔` |
| 有母兔但本批次无待分笼记录 | `C-02 的母兔（#104）在本批次没有待分笼记录` |
| 多只母兔都待分笼 | `C-06 有 2 只母兔待分笼（#102、#103），请在下方选择` |
| 一只母兔多条记录 | `母兔 #101 在本批次有 2 条待分笼记录，请在下方选择` |

文案里用裸笼号而不是带容量的完整标签：讨论母兔时「还可放 8 只」是噪声。

后两种不猜，落回下拉让人选。「一只母兔多条记录」原本列为待确认项，
现已用数据定调：`weaning_records` 上没有 `(batch_id, rabbit_id)` 唯一约束，
开发库 91 条记录里有 31 组同批次同母兔多条，但其中待分数量大于 0 的多条组为 0。
也就是说过滤后当下是一对一，但结构上不保证，所以保留这一分支而不是断言它不会发生。

用 `NfcCagePicker` 而不是 `NfcRabbitPicker`：后者的拒绝文案写死为「该笼位没有当前可选的兔只」，
而这里笼里往往有母兔，只是她没有待分笼记录——那句话是错的。
判据依赖记录级事实，只有调用方知道，这正是 `accepts` / `rejectReason` 留注入点的原因。

### 4.3 待摸胎状态下选配种公兔（recvtKdYobavMg）

宿主：`lib/src/ui/rabbits/sheets/entry.dart` 第 581 到 606 行的
`配种公兔` 下拉（key 为 `existing-rabbit-mating-male`），候选来自 `_availableBreedingMales`。

这一条是四个里最小的：`NfcRabbitPicker` 的 `candidates` 参数收的就是这样一个
`List<Rabbit>`，直接把 `males` 传进去，选中后写回 `_maleRabbitId`。
下拉保持不变。

同一个表单第 1792 到 1811 行还有一份配种字段（批量录入路径），
两处要同时接，否则同一个功能在两条路径上表现不一致。

### 4.4 批次详情分笼操作选兔笼（recvtKmvYQRGcV）

宿主：`lib/src/ui/batches/sheets/separation.dart` 的
`DropdownButtonFormField`（744 到 766 行），选项文案已经是
「笼号 · 商品兔笼 · 还可放 3 只」。

在下拉旁加 `NfcCagePicker`，合法目标限定为未满的商品兔笼。
拒绝文案要带上容量，满足第 5 条性质：「3-2-1 已放满 8 只，放不下了」，
而不是「该笼不可选」。

第 4 条性质在这里只生效一半。核实后确认：该弹窗一次只把一条待分笼记录提交到一个笼位，
`allocations` 长度恒为 1，没有多记录路径，也就不存在跳过项列表。

因此只保留「执行前说清范围」这一半：提交按钮上方常驻一行影响范围，
写明哪只母兔、待分几只、进哪个笼。提交后的结果由调用方已有的
「已分笼 N 只，剩余 M 只」覆盖。

## 5. 初始化的交互

写标签主流程已交付且经过真机验收，本节只覆盖 [design.md](design.md) §4.5 列出的三处缺口。

### 5.1 队列按排和层过滤

`GET /api/nfc/cages/write-queue` 按兔舍返回。大兔舍一次几百张，
贴标签的人站在某一排前面，队列却是从头到尾一条线。

分层笼位地图已经确立了「层是切换出来的空间」这个结构，队列复用同一套：
先选层，再选排，队列只列当前排。层签上沿用地图的做法带数量，
这里的数量是「本层还没贴的笼位数」。

层号 1 是最下面那一层，与 `app/.rule` 和 `admin/DESIGN.md` 保持一致。

### 5.2 收尾对账

写入会话结束后给一屏对账，把已写、跳过、待同步、失败四种结局分开列，
每种可展开看具体笼位。核心问题是「这个兔舍还剩哪些笼没有标签」，
所以对账屏的主数字是未贴数量，不是本次写了多少张。

### 5.3 待同步的可见性

`pendingSync` 现在只在进入 NFC 界面时补绑。贴完就退出的人不知道还有几张没同步上去。
未同步数量应当出现在 NFC 入口上，而不是只在界面内部。
是否改成后台补绑见 §7 待确认项 4。

## 6. 无障碍与窄屏

- 碰一下按钮是图标加文字，不做纯图标按钮。
- 等待态只改按钮文字（「碰一下目标笼位」变成「等待碰标签…」），不改按钮尺寸，
  避免 `app/.rule` 里禁止的布局跳动。
- 提示文案用 `maxLines` 加省略号兜底，长笼位标识不撑破容器。
- 360×800 与 200% 字号下，按钮与下拉纵向排列而不是并排。
- 成功与失败已经分别给触感和提示音，这是现场戴手套、不盯屏幕时的主要反馈通道，
  提取构件时不能丢。

## 7. 待确认项

1. 断网时跳过服务端核验直接选中（§3.2）是否可以接受。不接受的话，
   断网就只能走地图点选和输编号两条路，需要业务方确认现场能不能忍。
2. ~~一只母兔有多条待分笼记录时怎么办。~~ 已定：拒绝并点名有几条，落回下拉选（§4.2）。
3. 分笼多选时连贴同一张标签，是静默忽略还是提示「该笼已在本次范围内」。
4. `pendingSync` 是否改成后台补绑。改了要处理后台权限与电量，不改就得靠 §5.3 的入口提示。
5. 四个入口的碰一下按钮文案是否统一成「碰一下笼位」。
   现在 `move.dart` 用「碰一下目标笼位」，语义更准但四处上下文不同。

## 8. 验收

按 `docs/project/interaction-acceptance-spec.md` 第四节临时生成清单，仓库内不留业务步骤。
本专题必须走到的失败路径：

- 贴其它兔舍的标签。
- 贴未绑定的空白标签。
- 贴合法标签但目标笼不合法（满笼、停用、类型不符），每个入口各一次。
- 断网后贴标签。
- 多选场景里混入一个不合法目标，确认它被跳过且说得出原因。
- 360×800、200% 字号下走完一次完整选择。

NFC 尾段需要实体机人工验收。模拟器没有 NFC，脚本化 E2E 覆盖不到这一段，
v1.0.14 的发布回写里已经记录过这个限制。
