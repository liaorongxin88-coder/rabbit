## 1. 需求原文与拆解

> NFC的初始化要能够写标签数据，最好是将系统所有的兔笼里面有一个唯一的ID写进去，这个初始化的过程还需要考虑优化，包括后续碰了一下的功能使用也是，需要优化，需求小点我都写在这个需求点里面

这句话里有三件事：把唯一 ID 写进每个兔笼的标签、优化初始化过程、优化碰一下的使用。

## 2. 当前实现依据

### 2.1 载荷与绑定

标签写入的是一段自校验载荷，不是裸 ID：

```text
r1.<houseId-base36>.<cageId-base36>.<keyId-base36>.<signature-base64url>
```

签名是 HMAC-SHA256 截断到 12 字节。编解码在
`backend/rabbit-production/src/main/java/com/rabbit/app/modules/nfc/service/NfcCagePayloadCodec.java`。
带签名意味着一张伪造或串场的标签在解析阶段就会被拒绝，不必等到查库。

绑定关系落在两张表：`cage_nfc_tags` 是兔笼与标签的一一对应，`nfc_tags` 是泛化绑定，
用 `target_type` 与 `target_id` 指向兔只、批次或记录。

### 2.2 接口

`NfcController` 提供以下端点。

| 端点 | 用途 |
| --- | --- |
| `GET /api/nfc/cages/write-queue` | 取本兔舍待写入的兔笼队列 |
| `POST /api/nfc/cages/bind` | 写入成功后登记兔笼与标签的绑定 |
| `POST /api/nfc/cages/resolve` | 用载荷换回兔笼绑定视图 |
| `GET /api/nfc/resolve` | 用 tagUid 换回任意绑定目标 |
| `POST /api/nfc/tags`、`GET /api/nfc/tags`、`DELETE /api/nfc/tags` | 泛化标签的绑定、查询与解绑 |

### 2.3 客户端

| 文件 | 职责 |
| --- | --- |
| `app/lib/src/data/services/nfc/hardware.dart` | 会话、NDEF external 记录读写、写后回读校验 |
| `app/lib/src/data/services/nfc/ntag21x_writer.dart` | 非 NDEF 标签的裸写回退 |
| `app/lib/src/data/services/nfc/intents.dart` | Android `NDEF_DISCOVERED` 冷启动与前台分发 |
| `app/lib/src/data/services/nfc/capture_scope.dart` | 采集期间的独占标记 |
| `app/lib/src/ui/nfc/screens/{setup,write,error}.dart` | 初始化三屏 |
| `app/lib/src/ui/nfc/view_models/{queue,writer,pending_sync}.dart` | 队列、写入会话、离线待同步 |

Android 侧在 `app/android/app/src/main/AndroidManifest.xml` 声明 NFC 权限，
`android.hardware.nfc` 标为非必需，intent filter 限定
`scheme=vnd.android.nfc`、`host=ext`、`pathPrefix=/dzht.top:rabbit-cage`。

### 2.4 初始化会话已具备的能力

`NfcWriteController`（`app/lib/src/ui/nfc/view_models/writer.dart`）已经实现了连续写入所需的大部分东西：

- 会话存本地，杀进程后按 `currentIndex` 恢复，不用从头贴。
- 暂停、继续、跳过、回上一个。
- 标签上已有别人的数据时进入覆盖确认，不静默改写。
- 服务端返回 4606（标签已绑到别的笼）时进入重绑确认。
- 请求彻底发不出去时转入 `pendingSync` 本地队列，联网后补绑，写入不因断网作废。
- 成功与失败分别给触感和提示音，贴标签的人不用盯屏幕。
- 记住上一张写成功的 UID，识别「同一张标签重复贴」。

所以「初始化过程需要优化」这句话，指向的不是这条主链路。剩余可优化项见 §4.4。

## 3. 问题诊断

### 3.1 采集样板在每个入口重写一遍

五个界面各自实现了一遍「打开采集、消费事件、关闭复位」，共享的只有一个布尔 provider。

| 文件 | 文件行数 | NFC 相关行数 |
| --- | --- | --- |
| `app/lib/src/ui/rabbits/sheets/entry.dart` | 2543 | 41 |
| `app/lib/src/ui/rabbits/sheets/move.dart` | 671 | 42 |
| `app/lib/src/ui/reproduction/sheets/event.dart` | 1594 | 24 |
| `app/lib/src/ui/feed/screens/entry.dart` | 613 | 53 |
| `app/lib/src/ui/outbound/screens/flow.dart` | 1780 | 33 |

四个待做入口如果照旧接，就是第六到第九份复制。每份复制都要重新处理一次
取消、超时、解析失败、笼内没有符合条件的兔、权限不足这些分支，也就有六到九次写错的机会。

### 3.2 独占窗口是一个没有归属的全局布尔

`capture_scope.dart` 自己解释了为什么需要这个窗口：默认任何 NFC 事件都被
`app.dart` 接管并跳到笼位详情页，这对「贴一下看这个笼子」是对的，
对「贴一下选中换笼目标」是致命的，正在填的表单会被顶掉。

代价是这个标记没有归属。谁置位、谁复位全靠约定，异常路径上漏掉一次复位，
全局碰一下就永久失效，而且界面上没有任何提示，用户只会觉得「NFC 坏了」。
注释里写明这是刻意选择的朴素方案，理由是同一时刻只可能有一个采集界面在前台。
这个前提在四个新入口接进来之后仍然成立，但漏复位的风险随入口数量线性上升。

补充一个实际查到的缺陷，它比「漏复位」更早发作。归还标记是一次 provider 写入，
而 `dispose()` 和 `didUpdateWidget()` 都跑在框架的构建与卸载锁里。
在那里写 provider 会被 Riverpod 的调试断言拦下（它要对 `ProviderScope` 调
`markNeedsBuild`，而那个元素正被锁着），抛出
`Tried to modify a provider while the widget tree was building`。

触发动作很日常：点了碰一下，等标签的时候按返回退出弹层。
只有 debug 构建会抛，线上用户不受影响；但 debug 构建正是拿去做验收的那个包。
标记本身确实归还了（`StateNotifier` 先赋值再通知监听者），
所以问题不是标记卡死，而是逃逸出来的异常本身。

重要的是这不是抽取共享构件引入的。重构前的 `move.dart` 在 `dispose()` 里
同样同步写 `_captureFlag?.state = false`，两份原始实现都有，
只是从来没有测试碰过它。

### 3.3 从笼子换算到目标的规则各写各的

碰到的永远是一个兔笼，但各入口要的东西不同：换笼要笼本身，配种要笼内的种公兔，
填母亲兔 ID 要笼内的种母兔，投喂要笼内的全部在栏兔。这套换算和它的失败文案
目前分散在各入口内部，同一种失败在不同页面的说法不一致。

## 4. 设计

### 4.1 采集租约取代全局布尔

把 `nfcCaptureActiveProvider` 换成一个带持有者的租约：申请时拿到一个 token，
释放时必须交回同一个 token。这样做的收益有两个。

一是可以在租约上挂自动释放。界面销毁、路由弹出、超时未贴标签时释放，
不再依赖每个调用方都记得在 `finally` 里复位。

二是全局分发端（`app.dart`）能拿到「当前谁在采集」，
在日志和错误页里说得出是哪个界面占着，而不是只知道有人占着。

租约仍然只允许一个持有者。重复申请返回失败而不是排队，
因为同一时刻有两个采集界面本身就是缺陷，排队只会把它藏起来。

租约本身还是提案。已经落地的是一个更小的修正：共享构件把采集资源的回收
收口到唯一的 `_teardown()`，并为两个生命周期回调加了 `deferFlagRelease`：
本地状态仍然同步复位，只把标记归还用 microtask 推到锁释放之后，
并在那时检查 `flag.mounted`，避开整个 `ProviderScope` 已被拆掉的情况。
正常路径（按钮、事件回调）仍是同步写。

### 4.2 统一的碰一下选择器

新增一个共享构件，把五处样板收敛成一处。构件负责租约申请与释放、
等待与超时提示、解析失败与重试、取消返回；调用方只提供两件事：
要什么类型的目标，以及拿到目标后做什么。

界面形态沿用现在换笼弹窗的样子，因为它已经过真机验收。
构件同时要保留「碰一下」之外的另外两条路径：在笼位地图上点选、直接输入笼位编号。
分层笼位地图（`recvszXohbbWYC`）已经确立了这三条路径并存的交互，新入口不应只给 NFC 一条路。

### 4.3 目标解析策略

构件按目标类型分派解析，规则集中在一处：

| 目标类型 | 解析结果 | 失败情形 |
| --- | --- | --- |
| `CAGE` | 兔笼本身 | 笼位停用、容量不足、与来源笼冲突 |
| `BUCK_IN_CAGE` | 笼内在栏的种公兔 | 笼内没有种公兔、有多只需二次选择 |
| `DOE_IN_CAGE` | 笼内在栏的种母兔 | 笼内没有种母兔、有多只需二次选择 |
| `RABBIT_IN_CAGE` | 笼内在栏兔只集合 | 空笼 |

「笼内有多只符合条件」不是错误，落到二次选择列表，不要替用户猜。
判定用的在栏兔以服务端返回为准，不在客户端自行过滤，
这一点在笼位地图那次改造里已经踩过：客户端偷偷滤掉停用笼位，导致地图与实物对不上。

### 4.4 四个待接入入口

四个入口都用同一个构件，差别只在目标类型和后续动作。

| 入口 | 记录 ID | 目标类型 | 备注 |
| --- | --- | --- | --- |
| 商品兔转后备兔留种选兔笼 | recvtK5FSRTAyo | `CAGE` | 目标须为后备兔笼或空笼 |
| 场内生产入笼选断奶记录 | recvtK8yseN9jM | `DOE_IN_CAGE` | 由母兔反查其待分笼记录 |
| 待摸胎状态下选配种公兔 | recvtKdYobavMg | `BUCK_IN_CAGE` | 与 recvsUVpLZ09rx 同源，入口不同 |
| 批次详情分笼操作选兔笼 | recvtKmvYQRGcV | `CAGE` | 目标须为商品兔笼且未满 |

`recvtK8yseN9jM` 需要一次反查：碰到母兔之后要落到「这只母兔的哪一条待分笼记录」。
母兔可能有多条未分配完的记录，这时仍然落二次选择，不按时间猜最新的那条。

### 4.5 初始化流程的剩余优化项

主链路已经完整，剩下的是覆盖面和可观测性：

- 写入队列目前按兔舍取。大兔舍一次要贴几百张，队列里没有「按排、按层过滤」的入口，
  贴标签的人得从头翻到自己站的那一排。分层笼位地图已经有排和层的概念，队列可以复用。
- 会话结束后没有对账视图。已写、跳过、待同步、失败四种结局分散在会话状态里，
  贴完一轮之后无法一眼看出「这个兔舍还剩哪些笼没有标签」。
- `pendingSync` 的补绑时机依赖再次进入 NFC 界面。补绑发生在前台，
  用户如果贴完就退出，待同步项会一直挂着。

## 5. 异常边界

- 载荷签名校验失败按「不是本系统的标签」处理，不透出内部原因。
- 跨兔舍的标签在解析阶段拒绝，提示切换兔舍，不静默按当前兔舍解释。
- 采集期间收到的 NFC 事件不进入全局分发，不跳转笼位详情页。
- 租约超时或界面销毁时，正在进行的硬件会话必须停止，不留下后台读卡。
- 解析成功但业务校验不通过时，当场置灰并说明原因，不等提交时返回 400。

## 6. 待确认项

1. 租约超时时长。太短会打断动作慢的操作员，太长会让漏释放的窗口变大。
2. 「笼内有多只符合条件的兔」的二次选择，是弹列表还是直接取消并提示换个笼贴。
3. 写入队列是否要按排和层过滤，以及是否需要「本兔舍未贴标签清单」这个视图。
4. `pendingSync` 是否需要后台补绑，还是维持进入界面才补。
5. 标签丢失或损坏后的补办路径。当前解绑是 `DELETE /api/nfc/tags`，
   但没有约定现场发现标签读不出来时的处置顺序。

## 7. 验收

- 四个新入口各自的碰一下选择、地图点选、编号输入三条路径都能选中同一个目标。
- 采集期间贴标签不跳转笼位详情页，退出后全局碰一下恢复正常。
- 异常退出（返回键、杀进程、超时）之后，租约必须已释放。
- NFC 尾段需要实体机人工验收，模拟器不覆盖。
  这一点在 v1.0.14 的回写里已经记录过，脚本化 E2E 不能替代。
