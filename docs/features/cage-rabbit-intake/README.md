# 兔舍统一入笼与生产分笼约定

- 状态：业务已确认，进入实现
- 核对日期：2026-08-25
- 适用范围：Backend、Flutter App

本文约定兔舍笼位内新增兔只、断奶后的待分笼库存，以及幼兔父母关联。实现和验收必须同时满足本文，不能由客户端自行补齐服务端未返回的业务事实。

## 1. 业务词汇

| 词汇 | 含义 |
| --- | --- |
| 目标笼位 | 用户进入笼位详情后选定的入笼位置 |
| 兔只来源 | 本次新增兔只来自购入或场内生产 |
| 待分笼记录 | 完成断奶后形成的可分配幼兔库存，归属一个兔舍、生产批次和生产周期 |
| 分配项 | 一次请求中写入某个商品兔笼位的数量，以及可选的公母数量 |
| 父母关联 | 写入新建幼兔档案的 `mother_id`、`father_id`，默认不填写 |
| 生产来源 | 新建幼兔始终保留的 `birth_batch_id`、`birth_cycle_id` 和待分笼记录来源，不等同于父母关联 |

## 2. 入口和流程

统一入笼主入口位于兔舍笼位详情。操作顺序固定为：

```text
选定笼位 -> 选择来源 -> 填写来源资料 -> 确认 -> 提交 -> 刷新笼位与待分库存
```

### 2.1 购入

- 复用兔只单只建档接口。
- 用户选择种兔、后备兔或商品兔，笼位用途必须匹配。
- `arrivalMethod=0`。
- 录入流程不得伪造生产批次、生产周期或父母关联。

### 2.2 场内生产

- 仅适用于启用的通用空笼或商品兔笼。
- 用户先选择当前兔舍内未完成的生产批次，再选择 `waitingCount > 0` 的待分笼记录。
- 分笼实际创建商品兔，固定 `type=2`、`arrivalMethod=1`，并保存出生批次和出生周期。
- 一次笼位入口默认只分配到当前笼位，允许部分完成。服务端继续接受 allocations 数组，供批次入口和后续多笼编辑器复用。
- 批次详情可保留“待分笼”辅助入口，但必须复用同一表单和接口，不能形成另一套写逻辑。
- 断奶成功只生成待分笼记录并提示“去选择笼位”，不得自动打开批次专属分笼弹窗。

## 3. 公母数量

分配项保留总数，并允许成对提交公母数量：

```json
{
  "cageId": 12,
  "count": 4,
  "maleCount": 2,
  "femaleCount": 2
}
```

兔只性别编码固定为 `0=母`、`1=公`、`2=未知`。规则如下：

1. `count` 必填且大于 0。
2. `maleCount`、`femaleCount` 必须同时提供或同时省略。
3. 提供时，两者均不得小于 0，且两者之和必须等于 `count`。
4. 提供时，不得超过待分笼记录剩余的对应性别数量。
5. 旧客户端只提交 `count` 时继续兼容，但服务端不得推测性别；本次生成幼兔的 `gender` 写未知值 `2`。
6. 任一次部分分笼未提供公母数量后，该待分笼记录的 `waitingMaleCount`、`waitingFemaleCount` 都返回 `null`，后续不能从旧算法生成的兔只性别反推。
7. 新 Flutter 表单在待分笼记录具有完整且仍可信的剩余公母数据时要求填写本笼公母数量；历史记录或 count-only 分配使公母事实失真后，只填写总数并生成未知性别幼兔。

## 4. 可选父母关联

场内生产表单提供 `关联母兔（选填）` 和 `关联公兔（选填）`，两项默认均为“不关联”。

- 可以只填母兔、只填公兔、同时填写或都不填写。
- 母兔候选必须是当前兔舍的种母兔，公兔候选必须是当前兔舍的种公兔。
- 当前待分笼记录的母兔和生产周期公兔可以显示为推荐项，但不得自动选中。
- 父母选择只作用于本次请求创建的幼兔，不回写此前创建的幼兔。
- 未选择父母时，新建幼兔的 `mother_id`、`father_id` 必须为 `NULL`。
- 无论是否选择父母，`birth_batch_id` 和 `birth_cycle_id` 都必须保存。
- 父母兔可以已经离场，但必须仍是当前兔舍中的合法兔只档案。候选查询应标明离场状态。

父母字段位于请求顶层，因为一次请求中的所有分配项来自同一待分笼记录：

```json
{
  "requestId": "b57f...",
  "motherRabbitId": 101,
  "fatherRabbitId": 88,
  "allocations": [
    {
      "cageId": 12,
      "count": 4,
      "maleCount": 2,
      "femaleCount": 2
    }
  ]
}
```

## 5. 接口契约

### 5.1 查询

```http
GET /api/batches
GET /api/batches/{batchId}/weaning-records
```

客户端使用 `X-House-Id`，只展示当前兔舍未完成批次及 `waitingCount > 0` 的记录。待分笼响应至少包含：

```json
{
  "id": 501,
  "batchId": 20,
  "rabbitId": 101,
  "breedingCycleId": 301,
  "weaningDate": "2026-08-25T08:00:00+08:00",
  "weaningCount": 8,
  "waitingCount": 6,
  "maleCount": 4,
  "femaleCount": 4,
  "waitingMaleCount": 3,
  "waitingFemaleCount": 3
}
```

历史记录无法确定剩余公母数量时，`waitingMaleCount`、`waitingFemaleCount` 返回 `null`。

### 5.2 提交

```http
POST /api/batches/{batchId}/weaning-records/{weaningRecordId}/separation
```

成功响应：

```json
{
  "weaningRecordId": 501,
  "separatedCount": 4,
  "waitingCount": 2,
  "generatedRabbitIds": [9001, 9002, 9003, 9004],
  "replayed": false
}
```

客户端必须解析响应，成功后刷新目标笼位、当前兔舍兔只、批次和待分笼记录。

## 6. 事务、并发和幂等

- 服务端在一个事务中锁定批次、待分笼记录、父母候选和所有目标笼位。
- 批次必须属于当前兔舍且未完成，待分笼记录必须属于该批次。
- 目标笼位必须属于当前兔舍、已启用、为通用空笼或商品兔笼，且容量充足。
- 任一校验或写入失败时，兔只、笼位占用、待分数量、分配记录、批次关系和任务全部回滚。
- 同一业务草稿失败重试时复用 `requestId`。批次、记录、分配项、公母数量或父母选择发生变化时生成新 `requestId`。
- 相同 `requestId` 和相同载荷返回第一次提交的原始结果，不重复创建兔只或占用笼位。除 `replayed=true` 外，`separatedCount`、`waitingCount`、`generatedRabbitIds` 必须与第一次响应一致。
- 相同 `requestId` 和不同载荷返回冲突。
- 409 后客户端刷新笼位和待分记录，不得静默修改数量后自动重试。

## 7. 权限

- 查看批次和待分笼记录需要 `rabbit:batches:query`。
- 购入兔只需要 `rabbit:rabbits:add`。
- 场内生产分笼需要 `rabbit:batches:edit`。
- 客户端按来源分别判断权限，不能只依赖笼位页面的通用 `canEdit`。
- 服务端权限注解和 `X-House-Id` 校验是最终边界。

## 8. 兼容和数据变更

- 现有 `rabbits.mother_id`、`father_id`、`birth_batch_id`、`birth_cycle_id` 无需改表。
- 分配记录需要保存可选公母数量，用于计算剩余公母库存和审计。
- 迁移前已经存在的分配明细不视为具有可靠公母事实，新增公母列保持 `NULL`。没有历史分配的待分记录可以继续返回原始公母余额。
- 旧客户端的 count-only 请求继续可用，但生成未知性别幼兔，并使该记录后续剩余公母数变为 `null`。
- 新实现不得自动把待分笼记录母兔或生产周期公兔写入幼兔父母字段。

## 9. 验收

Backend 至少覆盖：

- 总数、公母数量、部分分笼和单请求多笼。
- 父母均空、只填一方、同时填写。
- 跨舍、错误类型、错误性别、停用笼位、用途错误和容量不足。
- 相同请求重放返回第一次的完整结果、同 ID 异载荷、待分数量并发变化和笼位容量竞争。
- count-only 生成未知性别，并使剩余公母数失去可推导性；显式公母分配逐次准确扣减。
- 未选择父母时父母字段为空，但出生批次和周期完整。

Flutter 至少覆盖：

- 笼位入口的购入与场内生产分支。
- 批次和待分记录过滤、当前笼位预选、部分分笼、公母输入和父母选填。
- 权限、加载失败、空状态、重复点击和 409 刷新。
- 360x800、412x915、键盘遮挡及 A059 真机流程。

总体门禁：后端单元测试、MySQL E2E、Flutter analyze、全量测试、Dev Debug APK、真机数据库断言和 `git diff --check` 全部通过。失败后修复对应实现并重跑失败门禁及其上层验收。
