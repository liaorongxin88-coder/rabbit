## 2. 现有实现

`GET /api/batches/{batchId}/statistics` 目前返回四个值，
SQL 在 `backend/rabbit-production/src/main/resources/mapper/modules/batch/BatchStatisticsMapper.xml`：

```sql
select count(l.id) as totalLitters,
       ifnull(sum(l.total_kits), 0) as totalKits,
       ifnull(sum(l.live_kits), 0) as totalLiveKits,
       ifnull(sum(l.weaned_count), 0) as totalWeaned
from batches b
left join litters l on l.house_id = b.house_id and l.batch_id = b.id
where b.house_id = #{houseId} and b.id = #{batchId}
group by b.id
```

这条查询已经覆盖了产崽窝数、产崽总数、活崽总数、断奶数量四个指标，是本次扩展的落点。

同目录下的 `BreedingPerformanceAggMapper.xml` 读的是 `parturition_records`、
`weaning_records`、`pregnancy_check_records` 这套旧表，且按兔只聚合而不是按批次，
不适合作为新指标的基础。V26 之后的权威来源是 `litters` 与 `repro_events`。

## 3. 取数映射

### 3.1 可以直接算出来的

| 指标 | 来源 |
| --- | --- |
| 配种日期 | `breeding_cycles.mating_date` 按批次取最小值 |
| 进行配种的母兔数量 | `breeding_cycles` 按 `batch_id` 去重 `mother_rabbit_id`，`mating_date` 非空 |
| 参与配种的公兔数量 | 同上，去重 `male_rabbit_id` |
| 确认怀孕的母兔数量 | `breeding_cycles.pregnancy_result` 为怀孕，或 `repro_events` 的 `PALPATION_PREGNANT` |
| 记录流产的母兔数量 | `repro_events` 的 `ABORTION`，按 `batch_id` 过滤 |
| 产崽窝数、产崽总数、活崽总数 | `litters` 的行数、`total_kits`、`live_kits` |
| 选留窝数、选留总数 | `litters.kept_kits` 大于 0 的行数、`kept_kits` 之和 |
| 断奶数量 | `litters.weaned_count` 之和 |
| 出栏数量 | `sale_order_items` 按 `batch_id_snapshot` 计数 |

`litters.batch_id` 可空，散养母兔不归属任何批次（V26 迁移注释里的业务裁定），
按批次聚合时这些行天然被排除，不需要额外条件。

`breeding_cycles` 上有两列结果字段：V21 加的 `pregnancy_result` 和 V26 加的 `result`。
取错一列会静默算出错误的受胎率，落 SQL 之前要先确认现役写入方向。见 §6 待确认项 9。

### 3.2 三处数据缺口

#### 缺口一：饲料没有批次归属，投喂量也没有分摊到兔只

`feed_logs` 有 `house_id`、`feed_time`、`amount`，没有 `batch_id`。
`amount` 是这一次投喂的整单总量，`feed_log_rabbits` 记录这一单喂了哪些兔，
但每只兔吃了多少没有落库。

两个料肉比都要求把饲料归到批次，所以需要一条分摊口径。可选的做法：

1. 按只均摊，`amount` 除以本单兔只数，再按兔归批次。实现最简单，
   但母兔和商品兔的采食量差一个量级，同一单里混着两类兔时误差直接进结果。
2. 按体重加权分摊。更接近事实，代价是要在投喂时点取到每只兔的体重，
   而 `rabbits.weight` 是可变的当前值，历史投喂无法回算。
3. 投喂时就按笼记账，给 `feed_logs` 或 `feed_log_rabbits` 补一列金额或重量。
   改动最大，但只有这条能让历史数据之外的部分算准。

归属规则本身在现有数据上是通的：母兔侧走 `batch_rabbits`
的 `join_date` 到 `exit_date` 窗口，商品兔侧走 `rabbits.birth_batch_id`。

#### 缺口二：断奶均重的分子没有落库

需求要的分子是「所有入笼操作总重量之和」。
`BatchRabbitEntryRequest` 收了 `totalWeight`，但 `BatchRabbitEntryService`
把它摊成单只重量写进 `rabbits.weight`（该文件第 234 行），入笼那一刻的总重没有留痕。

用 `sum(rabbits.weight)` 反推有两个问题：摊分时的取整误差会累积，
而且 `rabbits.weight` 是当前体重，兔子后续称重一次，这个数就不再是断奶时的值了。

`litters.avg_weaning_weight` 是另一个候选，但它是接产侧记录的窝平均值，
口径是「这一窝断奶时的平均重」，不等于「入笼总重除以断奶数量」。
两者在有寄养、有损耗时会分叉。

#### 缺口三：出肉率没有存储

需求写明这是屠宰场给的参数，不是系统算出来的。当前没有任何地方存它，
需要在批次上加一个可录入字段。附件表格里这一列同样大面积留空，
说明现场也不是每批都拿得到。

### 3.3 出栏与销售金额只在批量出库路径上准确

`sale_order_items` 有 `weight` 和 `price` 两列，但两条写入路径行为不同：

- `OutboundSubmitService` 走批量出库流程，写入 `item.setWeight(row.getWeight())`
  和 `item.setPrice(unitPrice)`，同时带上 `batch_id_snapshot`。
- `SaleService.create` 是旧的下单路径，显式写 `it.setWeight(null)` 和 `it.setPrice(null)`，
  重量和金额只存在订单级的 `sale_orders.total_weight`、`total_amount`。

因此按批次汇总出栏总重和销售金额，只能从 `sale_order_items` 逐条累加，
而这条路只对批量出库产生的订单成立。订单级的 `total_weight` 和 `total_amount`
不能直接用：一张订单可以混装多个批次的兔，按订单归批会重复计算。

另外 `price` 存的是单价而不是行金额（`OutboundSubmitService` 第 296 行传的是 `unitPrice`），
所以总销售金额要按 `sum(weight * price)` 算，不是 `sum(price)`。

## 4. 与现场表格的口径差异

附件《信达兔业繁殖计划》有三个工作表，其中「繁殖总表」和「料肉比统计」
是现场实际在用的算法。它和需求文字有四处不一致，都需要业务方拍板。

### 4.1 育肥期料肉比的分母

需求写的是除以出栏总重。附件「料肉比统计」表算的是除以育肥增重：

```text
育肥增加重量 = 总出栏重量 - 断奶总重量
育肥料肉比   = 育肥饲料用量 / 育肥增加重量
```

除以增重是饲料转化率的通行定义，除以出栏总重会得到一个偏小的数。
两者不能互相换算，必须选一个。

### 4.2 全程料肉比的分母

需求写的是出栏总重。附件算的是总出栏重量，且它包含转后备兔的重量：

```text
总出栏重量 = 出栏重量 + 后备重量（转后备数 × 转后备重量）
```

留种转后备的兔同样吃了这批的料，把它们的重量排除在分母外会高估料肉比。
附件里转后备兔按 1.75 到 2 kg 的固定值折算。

### 4.3 断奶均重的单位

需求写 kg。附件「繁殖总表」的断奶均重列是 810、900、976 这样的数，单位是克；
同一份文件的「料肉比统计」表里断奶重量又是 0.811、0.735，单位是千克。
展示单位需要统一，否则同一个数在两个界面差一千倍。

### 4.4 附件里有而需求里没有的指标

「繁殖总表」还有产仔率（产仔窝数/配种数量）、选留产子率（选留窝数/配种数量）
和精液贡献率三列。需求清单里没有这三项，但选留活崽率的定义
（选留总数/活崽总数）和附件的选留产子率是两回事，不要混。

## 5. 接口设计

在现有端点上追加字段，不新开端点：

```text
GET /api/batches/{batchId}/statistics
```

追加是安全的。Flutter 侧 `app/lib/src/domain/batches/statistics.dart`
只读它认识的四个键，多出来的键会被忽略；
Admin 侧 `admin/src/components/batch-statistics.tsx` 同理。

返回结构上，比率类字段应当返回分子分母而不是只返回算好的比值。
理由是分母为零时前端要显示「暂无数据」而不是 0%，
只给一个 `null` 比值无法区分「没有配种」和「配种了但没怀上」。

出肉率是录入值，读写分开：读走统计端点，写走批次自身的更新接口。

## 6. 待确认项

1. 「受胎数量」到底是配种母兔数还是确认怀孕的母兔数。
   按需求定义它等于配种数，按名字它等于怀孕数，而怀孕数已经单列在第 4 行。
2. 饲料分摊口径选 §3.2 缺口一里的哪一种，以及是否接受历史数据算不准。
3. 断奶均重的分子取哪个：补记入笼总重，还是改用 `litters.avg_weaning_weight`
   并相应改写需求里的定义。
4. 育肥期料肉比的分母是出栏总重还是育肥增重（§4.1）。
5. 全程料肉比的分母是否计入转后备兔的重量，以及折算重量取多少（§4.2）。
6. 断奶均重展示单位是克还是千克（§4.3）。
7. 走旧下单路径的历史订单缺少行级重量和金额，这部分批次的出栏与销售指标
   是显示为空还是回填。
8. 批次跨兔舍时如何归属。现有 `batches` 挂在单个 `house_id` 下，
   附件里的舍号加胎次才唯一标识一批，两者是否等价需要确认。
9. 受胎判定读 `breeding_cycles.pregnancy_result` 还是 `result`，
   或者一律以 `repro_events` 的 `PALPATION_PREGNANT` 为准。

## 7. 验收

- 用附件《信达兔业繁殖计划》里的一行真实数据造测试夹具，
  逐项比对系统算出的值与表格里的值，差异要能解释到具体口径。
- 分母为零时（未配种、未接产、未出栏的新批次）每个比率都返回空值而不是 0，
  界面显示为暂无数据。
- 混装多个批次的出库单，各批次的出栏数量与总重之和等于订单总量。
- 散养母兔（`litters.batch_id` 为空）不进入任何批次的统计。
- 单元测试放在 `rabbit-production`，跨模块的完整上下文用例才放 `rabbit-boot`。
