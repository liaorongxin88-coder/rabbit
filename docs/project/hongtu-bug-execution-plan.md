判断规则：

1. 8 月 31 日反馈提出的新口径，覆盖同一记录前面的旧表述。
2. 反馈判定失败且当前代码仍不符合时，进入修改。
3. 反馈判定失败但当前代码后来已补齐时，只安排复测，不重复开发。
4. 当前代码审计发现但 8 月 31 日反馈和需求详细描述都未要求的内容，不进入本轮。

## 2. BUG-01：商品兔断奶日期与成长阶段

### 2.1 原文关键点

| 编号 | 需求详细描述中的关键点 | 必须形成的结果 |
| --- | --- | --- |
| `K1-1` | “入场日期就为断奶的日期” | 继续使用现有 `arrivalDate` 存储，不新增第二个断奶日期字段 |
| `K1-2` | “需要在前端说清楚”“断奶日期需要说明一下” | 商品兔新增表单把“入场日期”显示为“断奶日期” |
| `K1-3` | “成长阶段这个参数是不需要填写的” | 商品兔新增时不显示、不提交手工成长阶段和进入阶段日期 |
| `K1-4` | 按断奶后的天数与适应期、成长期、育肥期时长判断阶段 | 成长阶段由系统自动计算 |
| `K1-5` | 原文给出两组精确日期区间 | 自动化测试必须逐日匹配这两组样例，不能只测试大致顺序 |

### 2.2 前端修改

Admin 修改 [rabbit-operation-dialogs.tsx](../../admin/src/components/rabbit-operation-dialogs.tsx)，Flutter 修改 [entry.dart](../../app/lib/src/ui/rabbits/sheets/entry.dart)：

1. 新增商品兔时，将 `arrivalDate` 字段标签改成“断奶日期”。种兔和后备兔仍显示原有日期名称，不扩大修改范围。
2. 商品兔新增表单删除“成长阶段”和“进入成长阶段日期”控件。
3. 商品兔创建请求不再提交用户选择的 `growthStage` 和 `growthStageEnteredAt`。
4. 保存后的阶段只展示服务端结果，前端不维护第二套阶段算法。

### 2.3 自动阶段修改

现有数据继续使用：

- `rabbits.arrival_date`：商品兔场景下表示断奶日期。
- `rabbits.growth_stage`：系统计算结果。
- `rabbits.growth_stage_entered_at`：当前阶段开始日期。

不新增 `weaning_date`，不创建 Flyway 迁移，也不做历史字段回填。

后端需要把商品兔的自动阶段边界收口到同一规则，并由创建和每日推进共用。当前每日推进 SQL 按 `阶段起始日 + 配置天数 <= 当天` 切换，必须用 Base 的精确样例检查是否提前一天。

Base 样例一：断奶日 `7月1日`，适应期 `3` 天，成长期 `10` 天，育肥期 `8` 天。

| 日期区间 | 期望阶段 |
| --- | --- |
| `7月1日` 至 `7月4日` | 幼兔适应期 |
| `7月5日` 至 `7月14日` | 成长期 |
| `7月15日` 至 `7月22日` | 育肥期 |
| `7月23日` 起 | 成熟期 |

Base 样例二：断奶日 `7月1日`，适应期 `4` 天，成长期 `15` 天，育肥期 `12` 天。

| 日期区间 | 期望阶段 |
| --- | --- |
| `7月1日` 至 `7月5日` | 幼兔适应期 |
| `7月6日` 至 `7月20日` | 成长期 |
| `7月21日` 至 `8月1日` | 育肥期 |
| `8月2日` 起 | 成熟期 |

主要修改 [RabbitService.java](../../backend/rabbit-production/src/main/java/com/rabbit/app/modules/rabbit/service/RabbitService.java)、`CommodityGrowthStage` 和 `RabbitMapper.advanceCommodityGrowthStages`。实现目标是创建后立即返回正确阶段，定时推进继续使用同一边界，不增加新的业务字段。

### 2.4 BUG-01 验收

- 两组 Base 日期样例逐日通过，特别检查每段最后一天和下一段第一天。
- Admin 和 Flutter 新增商品兔只显示“断奶日期”。
- 两端均没有成长阶段和进入阶段日期输入。
- 请求仍使用 `arrivalDate`，数据库不增加断奶日期列。
- 创建响应、详情和每日推进后的阶段一致。

## 3. BUG-02：投喂完成商品兔日常观察

### 3.1 原文关键点

| 编号 | 需求详细描述中的关键点 | 必须形成的结果 |
| --- | --- | --- |
| `K2-1` | 日常观察没有单独完成操作 | 不新增独立的观察确认入口 |
| `K2-2` | “完成相关投喂饲料即代表完成观察” | 成功投喂后，对应商品兔当日观察任务完成 |
| `K2-3` | “日常投喂饲料解决” | 用户通过现有投喂流程完成闭环 |

### 3.2 本轮处理

现有 `POST /api/feed-logs` 已包含投喂后完成任务的逻辑。本轮先增加真实 MySQL 集成测试，不预设需要修改生产代码：

1. 投喂商品兔后，完成对应兔只同一业务日的观察任务。
2. 未参与投喂的兔只任务保持待办。
3. 次日或其他日期任务不受影响。
4. 相同 `requestId` 重放只写入一条投喂记录，任务结果不重复。
5. 投喂事务失败时，投喂记录和任务状态一起回滚。
6. 首页、兔卡和笼位入口均不再显示已完成任务。

测试失败时，只修复投喂服务与任务写入链路；不新增独立接口，不增加新的页面按钮。

## 4. BUG-03：五段提醒使用兔舍周期

### 4.1 原文关键点与映射

| 编号 | 需求详细描述中的关键点 | 对应兔舍配置 | 本轮结果 |
| --- | --- | --- | --- |
| `K3-1` | 催情完成至配种 | `aphrodisiacDays` | 到期日使用当前兔舍值 |
| `K3-2` | 配种完成至摸胎 | `palpationDays` | 到期日使用当前兔舍值 |
| `K3-3` | 摸胎完成至备产 | `prepartumDays` 物理字段 | 按“摸胎至备产时长”解释并使用当前兔舍值 |
| `K3-4` | 接产完成至断奶 | `weaningDays` | 到期日使用当前兔舍值 |
| `K3-5` | 接产完成至结束休养 | `postpartumDays` | 到期日使用当前兔舍值 |
| `K3-6` | 不应再次出现“备产提前天数”描述 | Flutter 生产设置页及相关用户文案 | 改成“摸胎至备产时长”及对应说明 |

### 4.2 当前代码与必要修改

当前 `ReproStateMachineService` 已通过 `ReproSettingResolver.resolve(userId, houseId)` 读取当前兔舍配置。前四段和产后恢复先以非默认兔舍值复测，测试通过则不重写。

第三段仍按“预产期减提前天数”计算，并在 Flutter 设置页显示“备产提前天数”，与 Base 的“摸胎操作完成后至备产操作的等待时间”不一致。本轮按原文修改：

1. 用户文案改为“摸胎至备产时长”。
2. 状态机在摸胎结果为怀孕时，以摸胎操作日期加当前兔舍 `prepartumDays` 计算备产提醒。
3. 物理字段和对外 JSON 字段暂时保留 `prepartumDays`，避免无必要的数据库和接口迁移；领域语义名称改为“摸胎至备产等待天数”。
4. 清理用户可见的“备产提前天数”文案，代码注释和测试名称同步到新语义。
5. 现有兔舍配置值将按新语义解释。上线前由业务确认当前值是否需要调整；本计划不自动改写配置。

主要修改 `ReproSettings`、`DueDateCalculator`、`TransitionTable` 和 [production.dart](../../app/lib/src/ui/settings/screens/production.dart)。不增加事件参数快照，不修改 `repro_events.payload`，不新增迁移。

### 4.3 BUG-03 验收

为两个兔舍设置不同且明显区别于默认值的五组周期，逐项执行：

- 催情后核对配种提醒。
- 配种后核对摸胎提醒。
- 摸胎为怀孕后核对备产提醒。
- 接产成功后核对断奶提醒。
- 接产成功后核对结束休养提醒。

所有结果必须只使用操作所属兔舍的配置。Flutter 页面和操作流程中不得再出现“备产提前天数”。

## 5. BUG-04：首页兔舍和批次动态下拉

### 5.1 原文关键点

| 编号 | 需求详细描述中的关键点 | 必须形成的结果 |
| --- | --- | --- |
| `K4-1` | 兔舍使用动态下拉 | 选项来自当前账号可访问兔舍 |
| `K4-2` | 批次使用动态下拉 | 选项根据任务数据和所选兔舍动态变化 |
| `K4-3` | 8月31日批次已实现、兔舍未实现 | 重点验证兔舍下拉已补齐 |

### 5.2 当前状态与处理

当前 [overview.dart](../../app/lib/src/ui/home/screens/overview.dart) 已实现：

- 兔舍选项来自 `housesProvider`。
- 多于一个兔舍时显示“兔舍范围”下拉。
- 批次选项从任务数据动态汇总，并按所选兔舍收敛。
- 切换兔舍时清空原批次选择。
- 支持“全部兔舍”“全部批次”和“无批次任务”。

因此 BUG-04 不再安排接口或生产代码修改，只补原需求对应的 Flutter 回归测试和真机验收。测试失败时仅修复动态下拉本身。

明确排除：不为该 BUG 扩展 `/api/events` 的 `batchId` 或 `unbatched` 参数，不改为服务端筛选，不增加请求取消机制。这些内容不在需求详细描述中。

### 5.3 BUG-04 验收

- 账号只有一个兔舍时，不显示无意义的兔舍选择器。
- 账号有两个以上兔舍时，兔舍下拉列出全部有权访问的兔舍。
- 选择兔舍后，批次选项和任务列表只保留该兔舍内容。
- 切换兔舍后，旧批次选择被清空。
- 360x800 和 200% 字号下两个下拉可见、可选、无重叠。
