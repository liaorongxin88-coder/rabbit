### 一个绕不开的限制

两个提醒类需求由定时任务生成，`CommodityDailyCareReminderJob` 和 `EventReminderScanJob` 都是每天 `0 5 0`（00:05，Asia/Shanghai）触发，**代码里没有手动触发接口**。所以：

- 界面上当场点不出来，改完数据要等到第二天 00:05 之后才会出现在首页
- 想当场判定，用下面的 SQL 直接查 `work_tasks` 表

### SQL 兜底查询

```sql
-- 查某只兔子相关的所有待办任务
SELECT id, task_type, subject_type, subject_id, rabbit_id, batch_id,
       due_date, status, remark, create_time
FROM work_tasks
WHERE house_id = ? AND rabbit_id = ?
ORDER BY create_time DESC;

-- 查某只母兔在某批次里的成员关系是否还活跃
SELECT batch_id, rabbit_id, batch_role, is_active
FROM batch_rabbits
WHERE rabbit_id = ?;

-- 查某只母兔的繁育周期开闭状态和阶段时间
SELECT id, batch_id, mother_rabbit_id, stage, status,
       stage_entered_at, create_time
FROM breeding_cycles
WHERE mother_rabbit_id = ?
ORDER BY id DESC;
```

### A1. 一条繁育流程串起来，覆盖 9 条

**准备**：新建一个批次，放入 3 只种母兔（记为甲、乙、丙）。三只走不同分支。

| 勾选 | 步骤 | 核对点 | 预期 | 对应需求 |
| --- | --- | --- | --- | --- |
| [ ] | 建批次时不选任何母兔，先保存 | 能否建成 | 能建成空批次 | `recvqh3EJXzmO1` 子条款 |
| [ ] | 建完再往批次里加甲乙丙 | 三只都进来 | 成功 | 同上 |
| [ ] | 给甲配种，记下你填的操作时间 | 批次详情里甲的阶段时间 | **等于你填的操作时间**，不是当前系统时间 | `recvsV2P18D4Vd` |
| [ ] | 甲摸胎判「怀孕」，再记一次时间 | 同上 | 同上 | `recvsV2P18D4Vd` |
| [ ] | 乙配种后摸胎判「空怀」 | 乙在该批次里是否还显示活动中 | **显示活动已结束** | `recvsURZXJ6XAN` |
| [ ] | 丙配种后摸胎判怀孕，再执行流产 | 流产表单是否强制要求上传图片 | **不传图片提交不了** | `recvt82rWBOCHx` |
| [ ] | 丙流产完成后 | 丙在该批次里是否还显示活动中 | **显示活动已结束** | `recvsUPFjP1Jhb` |
| [ ] | 甲分娩后执行断奶，填留崽数 | 兔只列表里有没有立刻多出仔兔 | **不应该多出来**，此时只登记断奶记录 | `recvt6Qkxa4nHE` |
| [ ] | 断奶后甲在批次里的状态 | 是否显示活动已结束 | **显示活动已结束** | `recvsUSy6FpP9n` |
| [ ] | 对断奶记录执行分笼，指定笼位和公母数 | 这一步之后兔只列表 | **此时才生成商品兔对象**，数量与分笼填的一致 | `recvsUTRis0IpF` `recvt6UeydlX3S` |
| [ ] | 新建第四只母兔，创建时直接选「怀孕」等中间阶段入轨，加进同一批次 | 批次详情里这只兔的标签 | **有活跃标签**，和从头配种的兔子一样 | `recvt6Re55lzbJ` |

**三个容易误判的地方**：

1. **流产、空怀、分笼后如果你马上给同一只母兔再配种**，系统会在同一批次里开新周期，这只兔又会显示活动中。这是设计如此的连续繁殖，不是 bug。核对「活动是否结束」时，做完操作先别急着再配种。
2. 「分笼」在代码里就是 `WEANING` 之后的那一步实际落笼动作，需求文里的「分笼」和界面用词可能不完全一致，认操作语义不认名字。
3. 阶段时间同步这条，要**手动填一个和当前时间明显不同的操作时间**（比如填三天前），否则看不出区别。
