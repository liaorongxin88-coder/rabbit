# 交互验收规范

**这份文档不包含任何具体业务的验收步骤。** 它规定的是：任何**新交互**在被判定「可验收」
之前必须证明哪些性质，以及验收过程必须留下什么形状的产物。

具体到某次发布的业务清单（哪只兔、哪个批次、点哪个按钮）属于一次性产物，
每次**临时生成**，用完即弃，不进仓库。模板见 `docs/templates/acceptance-checklist.template.md`。

这样分的理由：业务步骤会随需求漂移，几个月后仓库里躺着的旧步骤比没有更糟——
它看起来像规范，实际是过期快照，读的人分不清哪句还作数。而下面这些性质不随需求变。

---

## 一、新交互必须证明的七条性质

新增或改动一个用户可见的交互时，逐条对照。**做不到的要写明为什么可以豁免**，
不能默认跳过。

### 1. 失败看得见

错误必须出现在**用户当前注视的位置**。

弹层、抽屉、底部表单里的提交失败，若用屏幕级的浮层提示（如 SnackBar），
会被弹层本身盖住——用户看到的是「点了没反应」。

> 实例：疫苗接种表单断网提交时，提示渲染在屏幕底部而被弹层遮挡，
> 真机验证才暴露，改为表单内错误条。单元测试和模拟器截图都发现不了这类问题。

**判定**：制造失败，截图必须能看到错误文案本身。

### 2. 失败不毁输入

提交失败后，弹层不关、已填内容保留、可直接改错重提。

**判定**：填写 → 制造失败 → 截图显示表单仍在且内容还在。

### 3. 重复提交只生效一次

网络慢时用户会连点。同一逻辑操作重复提交必须只产生一次效果。

**判定**：连点三次以上，用数据查询证明只产生一批记录（例如共用同一个 `requestId`）。
仅凭界面看不出来，必须查库。

### 4. 批量操作前后都要交代

批量操作在**执行前**说清影响范围，在**执行后**说清结果构成。

- 执行前：明确「将影响 N 只/N 个笼位」，不做无声批量
- 执行后：区分成功与跳过，**跳过项要能看到是哪一个、为什么**

整批失败通常是错的设计——现场按物理顺序作业，一个异常单元不该让整次操作作废。

**判定**：故意把异常单元（满的、停用的、缺数据的）放进范围，截图显示它被跳过并给出原因。

### 5. 边界被拦住且说得清

超过数量上限、超出取值范围时明确拒绝，提示要告诉用户**上限是多少**，
而不是只说「参数错误」。

上限本身要与底层写保护对齐，不能超过底层能承受的量。

**判定**：故意越界一次，截图显示拒绝文案。

### 6. 断网有活路

网络失败后必须留一条不把人卡死的路径。现场网络不稳是常态，不是异常。

**判定**：断网操作一次，截图显示用户仍有可选动作，而不是只能强退。

### 7. 窄屏大字号不塌

维持项目既有可达性基线：**360×800 分辨率、200% 字号**。

```bash
adb -s <serial> shell wm size 360x800
adb -s <serial> shell settings put system font_scale 2.0
# 验完必须还原
adb -s <serial> shell wm size reset
adb -s <serial> shell settings put system font_scale 1.0
```

**判定**：该基线下截图无溢出、无截断、操作区可点。

## 二、验收产物要求

### 截图

用 `scripts/acceptance-shot.sh <业务域> <说明>` 采集。它按业务域自动编号、
同步写入清单、失败不留空文件。

```text
artifacts/acceptance-<日期>/
  MANIFEST.md                        每张的时间、业务域、序号、说明
  <业务域>/<业务域>-<序号>-<说明>.png
```

业务域用两位数字前缀排序，顺序应贴合**真实作业流程**而非代码模块划分——
验收是在复现用户的一天，不是在遍历目录树。

### 一张截图只算一个事实

截图证明的是「看到了这个画面」，不等于「这件事成立」。

界面看不出来的（幂等、数据落库、定时任务产出），必须配**数据查询**作为证据，
并把查询和结果一并记入产物。

### 失败项要写现象

不通过的项记录**看到了什么**，不是只打叉。「点提交没反应，日志无请求」
比「不通过」有用得多。

## 三、防假通过

验收最常见的失效不是发现不了问题，是**根本没走到会出问题的那条路**。

| 陷阱 | 表现 | 破法 |
| --- | --- | --- |
| 只走顺路 | 挑干净数据提交，成功了就算过 | 每条交互至少走一次失败路径 |
| 时间同源 | 操作时间就用当前时刻，验不出时间同步 | 选一个和当前明显不同的时刻 |
| 界面推断数据 | 看列表没了就认为记录已关闭 | 查库确认状态字段 |
| 把设计当缺陷 | 状态流转后对象重新出现，误判为没结束 | 先确认旧记录是否已终结，再看当前状态 |
| 空库验批量 | 范围内全是可用单元，跳过分支没执行 | 故意混入异常单元 |

## 四、临时验收脚本的约定

具体业务的验收清单、造数脚本、查询脚本**每次临时生成**，放在仓库外
（例如 `/tmp/acceptance-run/`），不提交。

仓库里只保留两样：

- `scripts/acceptance-shot.sh`——与业务无关的采集工具
- `docs/templates/acceptance-checklist.template.md`——生成临时清单的模板

生成临时清单时，把模板里的占位段落替换为本次发布的实际业务域和步骤，
并逐条挂上本文第一节的七条性质。

---

## 五、环境要求

- 验收库**必须与开发库、生产库分离**，且用带真实积累数据的库而非空库——
  空库验不出迁移对存量的影响
- 涉及数据库迁移的发布，**迁移前**先查一次会被迁移改动的存量数据并留证，
  否则事后无法区分「异常数据」是迁移造成的还是本来就有的
- 设备访问本机后端用 `adb reverse tcp:<port> tcp:<port>`，避免依赖局域网地址
- 后端拒绝以占位符密钥启动是有意的安全守卫，验收环境应当场生成随机密钥，
  不要为图省事写进配置文件
